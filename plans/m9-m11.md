## M9 — Expanded mailer schema + transport resolution + proxy docs

### Types (`src/core.ts`, replacing `MailerName`)

```ts
export type MailerProvider =
  | "cf7" | "wpforms" | "formspree" | "formkeep" | "getform"
  | "resend" | "postmark" | "sendgrid" | "custom";

export interface MailerConfig {
  provider: MailerProvider;
  endpoint?: string;
  formId?: string;
  method?: "POST" | "PUT";          // default POST
  headers?: Record<string, string>;
  formToken?: string;               // public/form tokens only (Formspree-style)
  to?: string;                      // optional forwarded recipient hint (proxy)
}

export type MailerSpec = MailerProvider | "json" | MailerConfig;

// FormSpec:
//   mailer?: MailerSpec;
//   endpoint? and cf7? stay as legacy fallbacks (unchanged resolution order).
```

**Explicit deviation from the spec's interface:** `serverToken` (and any master
API key) is **excluded from the client-facing type** — it contradicts the
spec's own §3 secret isolation. It lives only in the proxy `.env` boilerplate.
`apiKey` in the spec's interface is documented as *public/client tokens only*
(`formToken` here).

### Resolution (`src/mailers/`)

- `MailerConfig` becomes the single normalized config shape — absorbs today's
  `config.endpoint` / `config.apiUrl` / `config.formId` props.
- `getMailer()` → `resolveMailer(spec, config)` with precedence:
  runtime `config` props → `mailer` config object → legacy top-level
  `endpoint` / `cf7` blocks → build-time console warning (unchanged `no
  env-var assumptions` rule).
- `"json"` shorthand and `provider: "custom"` both land on the existing
  generic FormData/JSON transport (extended to honor `method` / `headers`).
- Unknown provider names: fall back to `cf7` (existing behavior) + warning.

### Adapters (two tiers)

**Direct (client → provider, config/URL shaping only, no secrets):**

| provider | transport behavior |
| --- | --- |
| `cf7` | existing CF7 REST feedback mailer (unchanged) |
| `wpforms` | POST to `{endpoint}/wp-json/wpforms/v1/forms/{formId}/submit` (verify exact route during implementation) |
| `formspree` | POST `https://formspree.io/f/{formId}` with `Accept: application/json` |
| `formkeep` | POST `https://formkeep.com/f/{formId}` (or explicit `endpoint`), optional JSON accept |
| `getform` | POST given `endpoint` or `https://getform.io/f/{id}`, multipart/form-data |

**Proxy-only (`resend` / `postmark` / `sendgrid`):** the client POSTs JSON
`{ provider, formId, to, payload }` (canonical data as a JSON object, not
FormData) to the consumer-supplied `endpoint` (default `/api/contact`). The
provider name is carried so the proxy can forward correctly; the client never
holds a key.

### Markup / serialization

- `renderFormShell` serializes the **resolved provider name** into
  `data-mailer` and the client-safe config (`endpoint`, `formId`, `method`, …)
  into `data-*` attributes so the specless `initForms` path still resolves
  config-object mailers.
- New `data-*` attributes added **only via `markup.ts`** (single source of
  truth) and pinned by regenerated fixtures (`RECORD=1 npm test`, diff
  reviewed).

### Proxy docs + boilerplate

- New `docs/transport-proxies.md`: Next.js (App Router) route handler + Astro
  endpoint boilerplate, both **raw `fetch`** to provider REST APIs with
  `Bearer` keys from `RESEND_API_KEY` / `POSTMARK_SERVER_TOKEN` /
  `SENDGRID_API_KEY`.
- Zero package deps even in the example — stays within the zero-runtime-dep
  rule.
- Nodemailer-over-SMTP becomes an optional worker variant inside this doc
  (this **re-scopes the roadmap's v0.4.0 Nodemailer item**).

### Tests / docs / state

- Tests: resolver precedence (props > config > legacy), shorthand/config/
  unknown mapping, direct-provider URL + body shaping, proxy JSON payload
  shape, `method` / `headers` honored, legacy `mailer: "json"` preserved
  (including the `fail-m8`-style fetch stub patterns), serialization
  assertions + regenerated fixture diff.
- README mailer section + `/mailers` demo gain a provider-config tab (no
  secrets).
- FEATURES.md ↔ `project.state.json` **+4 rows**: `mailer-config`,
  `mailer-direct-providers`, `mailer-proxy-docs` (names TBD at implementation).

## M10 — Structural additions: `callout` + `html`

- `src/core.ts`:

  ```ts
  export interface CalloutSpec {
    type: "callout";
    text: string;
    variant?: "info" | "warning" | "success" | "danger";
  }
  export interface HtmlSpec {
    type: "html";
    html: string;   // verbatim; sanitization is the consumer's responsibility
  }
  ```

- Both are decor-style `FormElement`s — render-only, **dropped from the client
  spec**, never validated or sent (same treatment as `heading` / `section`).
- `markup.ts` builders (`renderCallout` / `renderHtml`) + `--rf-callout-*`
  theme tokens; fixtures `struct-callout.html` / `struct-html.html` pinned via
  `RECORD=1` + reviewed diff. Engine untouched.
- Demos: `callout` on the field-types or conditional page; a consent `html`
  block in the wizard. README + examples-README note the sanitization
  responsibility.
- FEATURES ↔ state.json **+2 rows**: `struct-callout`, `struct-html`.

## M11 — Declarative `FormSpec.analytics` (hybrid with the existing seam)

The seam today is `createAnalytics({ adapter: { track(event, detail) } })`
dispatching the whole `rf:*` bus. The declarative block resolves to a built-in
**adapter** — no fabricated events browser-side.

### Types (`src/core.ts`)

```ts
export type AnalyticsProvider = "dataLayer" | "customEvent" | "plausible" | "posthog";

export interface AnalyticsSpec {
  enabled?: boolean;              // default true when the block is present
  provider?: AnalyticsProvider;   // default "dataLayer"
  eventName?: string;             // submit-success event name; default "form_submitted"
  trackSteps?: boolean;           // rf:step-change → form_step_view
  trackFieldErrors?: boolean;     // rf:validation-error → form_validation_error
}
```

### `resolveAnalytics(spec)` in `src/runtime/analytics.ts`

Returns a `createAnalytics`-compatible object routing the existing bus:

- `rf:step-change` → `form_step_view` (props: `formName`, `stepTo`, `stepTotal`).
- `rf:validation-error` → `form_validation_error` (props: `formName`,
  `failedFields` list).
- `rf:submit-success` → `eventName ?? "form_submitted"`.
- `rf:submit-error` → `eventName` with `outcome: "error"`.

Provider routing (consumer-loaded globals, zero deps):

- `dataLayer` — `window.dataLayer` push.
- `customEvent` — window `CustomEvent` dispatch (uniform event names).
- `plausible` — `window.plausible(name, { props })` when available.
- `posthog` — `window.posthog.capture(name, props)` when available.

### Seam extension (backward-compatible)

`AnalyticsTracker.track(event, detail, form?)` — optional `form` gives built-in
adapters `form.dataset.mailForm` / `form.id` for `formName` / `formId` in every
push (`rf:step-change` detail only carries `{ from, to, total }`). Existing
consumer adapters ignore the new arg; M6 scope/docs unchanged.

### New bus event: `rf:validation-error`

`trackFieldErrors` needs a real signal; the bus has none today. Emit
`rf:validation-error` (detail `{ name, id, errors: [{ name, message }], count }`)
on the submit path **and** the live-validation gates. New **event only** — no
new `data-*` markup, so fixtures are unaffected. Documented in README events
table + tested.

### Wiring (hybrid)

`AttachOptions.analytics?: false | ReturnType<typeof createAnalytics>`:

- absent → engine auto-resolves `spec.analytics` (when present) and attaches
  it; the subscription is held and detached in `detach()`.
- explicit value → overrides the block.
- `false` → opts out.
- standalone `createAnalytics` seam keeps working exactly as today.

### Tests / docs / state

- Adapter routing per provider (happy-dom: dataLayer / customEvent pushes).
- Auto-attach on `attachForm` / `renderForm` / `initForms`; explicit override;
  `false` opt-out.
- `rf:validation-error` on submit + live-gate failures.
- README analytics/events sections.
- FEATURES ↔ state.json **+2 rows**: `analytics-block`, `validation-error-event`.
